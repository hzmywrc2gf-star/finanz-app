# Projektkontext: finanz-app („Finanzklar“)

Persönliche Finanz-PWA (Deutsch, mobil zuerst, Apple-Stil). Nutzer ist kein Entwickler; Antworten auf Deutsch, kleine Schritte, alles vor „fertig“ verifizieren (Tests + `npm run e2e` + Screenshots).

## Stack
React 19 + Vite + TypeScript, vite-plugin-pwa (autoUpdate, precache), Vitest. Keine UI-/Chart-Libraries – Balken in CSS. `base: './'` für GitHub Pages (Deploy via `.github/workflows/deploy.yml`, Push auf `main`).

## Architektur
- `src/domain/` – reine Logik, ohne React: `types.ts` (AppData v5), `money.ts` (Cent ↔ „1.234,56 €“, `parseEuroInput`), `dates.ts` (lokale ISO-Daten, Monatshelfer), `calc.ts` (`accountBalance(data,'konto'|'bargeld')`, `totalBalance`, `compareTransactionsDesc`, gemeinsamer Bereichshelfer `summarizeRange`), `ledger.ts` (Buchungen + Umbuchungen gemischt, Suche, Monatsgruppen), `recurring.ts` (Terminplan, `bookDue`, `pendingConfirmations`, `upcoming` mit `excludeCategoryIds`, `monthlyEquivalent`), `month.ts` (`monthSummary` inkl. Vormonat/Sparquote/Top-5, `monthTrend`, `niceAxisMax`), `budget.ts` (`monthBudgets`, `budgetAlerts`, Status ok/warn/over per exaktem Integer-Vergleich), `defaults.ts`.
- `src/data/` – Persistenz: `repository.ts` (async Interface `load/save`), `localStorageRepo.ts` (Key `finanz-app:v1`), `backup.ts` (JSON-Export, strikte Import-Validierung), `migrate.ts` (v1→v2→v3→v4→v5, genutzt von Repo und Backup-Import). Der localStorage-Key bleibt `finanz-app:v1` (Umbenennung würde Daten verwaisen); die Version steckt im Datensatz.
- `src/state/` – `actions.ts` (pure Reducer-Funktionen inkl. `setCategoryBudget`, werfen deutsche Fehler), `FinanceContext.tsx` (`useFinance()` Hook). UI nutzt nur diesen Hook.
- `src/domain/gesture.ts` – reine Gestenlogik (Schwellen, `gestureIntent`, `swipeDecision`, `releaseVelocity`, `rubberBand`, `animationMs`), getestet in `gesture.test.ts`. `src/hooks/useDragGesture.ts` (Pointer-Events-Erkennung, rAF, Pointer Capture), `src/lib/motion.ts` (`EASE_IOS`, `reducedMotion`, `afterTransition`, `isFormField`, `modalOpen`).
- `src/components/`, `src/pages/` (Start, Alle Buchungen, Bargeld, Verträge, Monat, Budgets, Einstellungen), Navigation per Tab-State (kein Router). Styles in `src/index.css` (CSS-Variablen, Dark Mode, Safe Areas).

## Regeln
- Datenmodell v5 (v4 + `RecurringRule.autoBook: boolean`, Migration v4→v5: alle bestehenden Verträge `true`; Backup validiert das Feld strikt): `Transaction.account: 'konto' | 'bargeld'` (Migration v3→v4: alles `'konto'`), `Settings.startCashCents`, `AppData.transfers` (`Transfer`: `direction` `'withdrawal'` = Abhebung Konto→Bargeld, `'deposit'` = Einzahlung Bargeld→Konto, positive Cent, Datum, optionale Notiz). Umbuchungen sind weder Einnahme noch Ausgabe: Monatsauswertung, Budgets und Kategoriesummen betrachten nur `transactions`. Bar-Buchungen zählen dort wie jede andere Buchung. Wiederkehrende Buchungen buchen immer aufs Konto. Bargeld darf negativ werden (wird rot angezeigt).
- Start-Navigation: Tab „Start“ hat genau eine Unterebene (`StartView` in `App.tsx`: Übersicht, Alle Buchungen, Bargeld, Verträge) mit iOS-Navigationsleiste (`SubPageHeader`, Zurück-Knopf `aria-label="Zurück"`). Jeder Tab-Wechsel (auch Tippen auf „Start“) setzt auf die Übersicht zurück; jede Navigation scrollt nach oben. Übersicht: Kontostand (+ „Bargeld … · Gesamt …“), Knopf „Buchung hinzufügen“ inline darunter (kein schwebender Fab auf der Startseite, er würde die letzte Zeile verdecken), Budget-Hinweis, „Demnächst fällig“, Liste mit drei Zeilen. Keine „Letzten Buchungen“ mehr.
- „Demnächst fällig“ blendet Verträge der Kategorie Gehalt (`builtInId('income','Gehalt')`) aus; andere Einnahmen bleiben. „Verträge“ ist die UI-Bezeichnung der wiederkehrenden Buchungen (Domain-Namen bleiben `recurring`); Fixkosten pro Monat = `monthlyEquivalent` (nur aktive Ausgaben-Verträge, quartalsweise ÷3, jährlich ÷12, je Regel mit `Math.round` auf ganze Cent).
- Beträge immer als positive ganze Cent (`amountCents`), Art über `kind`. Nie Floats rechnen.
- Daten als `'YYYY-MM-DD'` in lokaler Zeit, nie `toISOString()`.
- Je Art gibt es eine `builtIn`-Kategorie „Sonstiges“ (nicht löschbar/umbenennbar); gelöschte Kategorien → Buchungen nach „Sonstiges“.
- Datenmodell-Änderungen: `version` erhöhen + Migration in Repo und Backup-Import.
- Wiederkehrende Buchungen (`AppData.recurring`): `bookedThrough` = alles bis dahin ist erledigt (nur vorwärts). `bookDue` (idempotent) läuft nach dem Laden, bei `visibilitychange` und stündlich im `FinanceContext`; gelöschte erzeugte Buchungen kommen nicht zurück. Tag 29–31 → Monatsletzter. Buchungen tragen `recurringId` (darf auf gelöschte Regeln zeigen).
- Automatisch buchen (`RecurringRule.autoBook`): `bookDue` bucht nur Regeln mit `autoBook = true`; manuelle Regeln (`false`) werden komplett übersprungen, ihr `bookedThrough` rückt nicht von selbst vor. `pendingConfirmations(data, today)` liefert je manueller Regel die Termine in (bookedThrough, today] als `{rule, date}` (Datum aufsteigend, dann Titel). Actions: `confirmOccurrence` / `skipOccurrence` (nur der älteste offene Termin, sonst Fehler „Bitte zuerst den älteren Termin bestätigen.“; Buchung immer aufs Konto, mit `recurringId`, `bookedThrough` = Termin), `bookNextNow` („Jetzt buchen“: der älteste unerledigte Termin, auch in der Zukunft; Buchungsdatum frei wählbar; Fehler bei beendetem Vertrag). Wechsel auf automatisch bucht offene Termine sofort (`FinanceContext.updateRecurring` ruft danach `bookDue`); Wechsel auf manuell behält `bookedThrough`. Beim Anlegen einer manuellen Regel bedeutet „Nachbuchen“ = „Als offen anzeigen“. Start: Karte „Zu bestätigen“ direkt unter dem Kontostand (je Vertrag nur der älteste Termin + „+N weitere offene Termine“), Buttons „Buchen“ (TransactionForm im `booking`-Modus) und „Überspringen“. Vertragsliste: Hinweis „bestätigen“ bei manuellen Regeln.
- Monatsbudgets: `Category.monthlyBudgetCents` (nur Ausgaben, positive Cent, fehlt = kein Budget). Gezählt werden nur gebuchte Ausgaben des Kalendermonats (keine geplanten). Schwellen: ab 80 % warn, über 100 % over. Start zeigt Hinweiskarte bei warn/over.
- Gesten und Übergänge (nur Pointer Events + CSS-Transform/Transition, keine Bibliothek; Animationen schreiben per Ref in `style`, kein React-State pro Frame): 
  - Absicht: erst ab 8 px Bewegung, Hauptachse > 1,5 × Nebenachse („klar waagrecht/senkrecht“), sonst bleibt Scrollen/Tippen unberührt; erst dann Pointer Capture (danach kein `click` auf das Ziel). Container haben `touch-action: pan-y`.
  - Zurück-Wischen (`StartStack`): Start nur bei x ≤ 24 px, nicht auf Eingabefeldern, nicht bei offenem Sheet/Dialog (`[aria-modal]`). Unterseite folgt dem Finger, Übersicht darunter (Parallaxe −30 % → 0, Abdunkeln). Loslassen: zurück bei > 35 % der Breite oder > 0,5 px/ms und > 30 px, sonst Federn zurück (250 ms, `EASE_IOS`). Push/Pop per Knopf ~300 ms. Übersicht und Unterseite liegen nur während der Bewegung gleichzeitig im DOM (`.stack[data-phase]` ≠ `idle`; die Übersicht ist dann `position: fixed`, die Unterseite bleibt im normalen Fluss, damit weiter das Fenster scrollt). Der schwebende „+“ wird währenddessen ausgeblendet (fixed-Kinder einer transformierten Seite wären falsch positioniert).
  - History: Jede Unterseite = ein `history.pushState({sub})`-Eintrag; Zurück-Knopf/Wischen rufen `history.back()` (popstate setzt die Ansicht; Knopf animiert, System-Zurück nicht, weil das OS schon animiert). Tab-Wechsel auf einer Unterseite ruft `history.back()` (kein Rest-Eintrag, kein doppeltes Zurück). Nach Neuladen wird ein übrig gebliebener Eintrag per `replaceState` verworfen. `popstate` entscheidet nur anhand von `event.state`.
  - Sheet (`Sheet.tsx`): Griff + Kopfzeile (sticky, `touch-action: none`) ziehen, oder irgendwo, wenn der Inhalt oben ist; bei Sheets, deren Inhalt ohne Scrollen passt (`data-fits`), überall. Nicht auf Buttons/Feldern. Schließen bei > 30 % der Höhe oder > 0,5 px/ms; nach oben Rubber-Band (max. 80 px); Hintergrund (`.backdrop-dim`) blendet mit. Jedes Schließen (Abbrechen, Escape, Hintergrund, Wischen) animiert aus und ruft danach `onClose` (Eingabe wird wie bei „Abbrechen“ verworfen); „Sichern“ schließt sofort. `dismissible={false}` (verschachteltes „Jetzt buchen“) sperrt das Schließen. `ConfirmDialog`: Scale-in/-out (150 ms).
  - Monat/Budgets (`SwipePane`): waagrechtes Wischen (nicht ab dem linken 24-px-Rand, nicht auf Feldern) → links = nächster, rechts = vorheriger Monat; Inhalt folgt mit Widerstand (max. 40 % der Breite), Schwelle 25 % oder Flick; alter Monat gleitet aus, neuer von der Gegenseite ein. Nur Inhalt wird bewegt, `position: fixed`-Kinder (Fab, Sheets) liegen außerhalb. Tippen ≠ Wischen (Diagrammspalten bleiben tippbar).
  - Wischen zum Löschen (`SwipeRow.tsx`, in `TransactionRow`/`TransferRow`: Alle Buchungen, Bargeld, Monat „Größte Ausgaben“ und „Alle Buchungen“): Zeile nach links ziehen (gleiche Absicht wie überall, `useDragGesture`), der Inhalt folgt, dahinter erscheint die rote Aktion „Löschen“ (80 px, `ROW_ACTION_PX`). Loslassen entscheidet `rowSwipeOutcome` (`gesture.ts`): > 50 % der Aktion = offen, > 60 % der Zeilenbreite oder Flick (> 0,5 px/ms) über die Aktion hinaus = sofort löschen (Zeile gleitet raus, Höhe klappt zu, ~200 ms; Bewegung reduzieren: nur Ausblenden), sonst Federn zurück. Nur eine Zeile ist offen (Modul-Variable `openRow`); Tippen außerhalb, Scrollen oder Öffnen einer anderen Zeile schließt sie, Antippen des Inhalts einer offenen Zeile schließt nur (kein Bearbeiten-Sheet), Ziehen nach rechts schließt. Kein Rechts-Wischen als Aktion. Der Löschen-Knopf ist ein echter Button (`aria-label="Löschen: <Titel>"`) und bei geschlossener Zeile `visibility: hidden` (`data-swipe="closed"`). Vorrang: Kanten-Wischen (x ≤ 24 px) startet nie ein Zeilen-Wischen; ein Zug, der auf einer Zeile beginnt (`[data-swipe-row]`, `inSwipeRow`), gehört der Zeile und startet keinen Monatswechsel (`SwipePane`), ein Zug daneben wechselt weiter den Monat; nicht auf Feldern, nicht bei offenem Sheet. Der Weg ohne Geste bleibt: Tippen auf die Zeile → Sheet → „Buchung/Umbuchung löschen“ (mit `ConfirmDialog`).
  - Rückgängig-Toast (`UndoToast.tsx`, vom `FinanceProvider` gerendert): jedes Löschen (Wischen oder Sheet) über `deleteTransaction`/`deleteTransfer` merkt das gelöschte Objekt; unten über der Tab-Leiste „Buchung gelöscht“/„Umbuchung gelöscht“ + „Rückgängig“ (`role="status"`, nur solange sichtbar im DOM), verschwindet nach 5 s (`UNDO_MS`); nur das jüngste Löschen ist rückgängig machbar. Wiederherstellen per reine Actions `restoreTransaction`/`restoreTransfer` (exakt dasselbe Objekt, gleiche id/createdAt/recurringId/account; Fehler, wenn die id schon existiert); `bookedThrough` wird nicht angefasst. `replaceAll` (Import) verwirft den Toast.
  - Haptik (`src/lib/haptics.ts`, `haptic()`): `navigator.vibrate(10)` wenn vorhanden (Android), sonst iOS-18-Fallback: ein einziges verstecktes `<label><input type="checkbox" switch></label>` (aria-hidden, tabindex −1, nicht `display: none`, Fokus wird zurückgegeben), das per `label.click()` umgeschaltet wird (Safari 18 spielt dafür den System-Haptik-Tick); sonst No-Op, wirft nie. Aufruf synchron im Event-Handler: Speichern einer Buchung (auch Bestätigen/„Jetzt buchen“) oder Umbuchung, Überspringen eines Termins, Löschen (Wischen oder Sheet), Rückgängig – nicht bei jedem Tippen. Grenze: iOS < 18 und Safari ohne `switch`-Unterstützung haben keine Haptik; ob der Tick auf dem echten iPhone spürbar ist, lässt sich nur dort prüfen.
  - Tab-Wechsel: Einblenden 150 ms (`.tab-fade`). Tippfeedback: `touch-action: manipulation`, `user-select: none` auf Buttons/Zeilen, `:active` sofort (Zeilen dunkler, Buttons Opacity/Scale 0,97).
  - „Bewegung reduzieren“ (`prefers-reduced-motion`): keine Slides/Federn, nur Überblendung ≤ 120 ms (`animationMs`, `reducedMotion()`); Gesten funktionieren weiter, schließen aber ohne lange Animation.
- Darstellung (Automatisch/Hell/Dunkel): Geräte-Einstellung, kein Teil von `AppData`/Backup/Migration. Eigener localStorage-Key `finanz-app:theme` mit `'light' | 'dark'` (Automatisch = Key fehlt; ungültig oder Speicher gesperrt → Automatisch, jeder Zugriff in try/catch). Logik in `src/lib/theme.ts` (`resolveTheme`, `getThemePref`, `setThemePref`, `applyTheme`), Hook `useThemePref`, UI als erste Sektion „Darstellung“ in den Einstellungen (wirkt sofort). Angewendet über `document.documentElement.dataset.theme` (`light`/`dark`; bei Automatisch Attribut entfernt). CSS: dunkle Palette in `@media (prefers-color-scheme: dark) { :root:not([data-theme='light']) {…} }` plus identischer Block `:root[data-theme='dark']` (beide beim Ändern der Palette pflegen); `color-scheme` per `:root[data-theme=…]`. Neue Dunkel-Styles nie als nacktes `@media (prefers-color-scheme)` schreiben, sondern über die CSS-Variablen oder dieses Selektor-Muster. Inline-Skript im `<head>` von `index.html` setzt `data-theme` vor dem ersten Rendern (kein Aufblitzen; Key dort und in `theme.ts` identisch halten). `theme-color`-Metas: bei erzwungenem Thema beide auf #F2F2F7 bzw. #000000, bei Automatisch zurück auf ihre media-Werte (`applyTheme`, auch beim Start in `main.tsx`); `apple-mobile-web-app-status-bar-style` bleibt `default`.
- Neues Backend: neue Klasse, die `FinanceRepository` implementiert; UI bleibt unverändert.

- Monatsauswertung (`MonthPage`): nur gebuchte Buchungen des Kalendermonats, Vergleich zum Vormonat (mehr Einnahmen/Saldo = gut, mehr Ausgaben = schlecht), Verlaufsdiagramm in CSS (Einnahmen links, Ausgaben rechts, gemeinsame Achse ab 0) mit Tabelle als Nicht-Farb-Fallback. Ganz unten „Alle Buchungen“ des Monats (neueste zuerst, `monthSummary.transactions`, Tippen öffnet das Bearbeiten-Sheet) und „+“ (Fab; Datum = heute im aktuellen Monat, sonst der 1. des angezeigten Monats). Es gibt keine Wochenansicht mehr. Kein Datenmodell-Update nötig.

## Verschlüsselung (Teil A: Krypto-Kern + verschlüsselte Backups; Teil B = App-Sperre, noch offen)
- Nur Web Crypto API (`crypto.subtle`), keine Krypto-Bibliothek, nichts Selbstgebautes. Code in `src/lib/crypto.ts` (rein, async, Tests in `crypto.test.ts` mit Nodes webcrypto), Backup-Anbindung in `src/data/backupCrypto.ts` (`exportEncrypted(data, pw)`, `decodeBackupFile(text, pw?)`, `isEncryptedBackup`); UI nur in `BackupExportSheet`/`BackupImportSheet`, Krypto bleibt aus den Komponenten heraus.
- Parameter (Konstanten): PBKDF2-SHA-256, `PBKDF2_ITERATIONS = 600_000`, Salt 16 Byte zufällig; Passwort → `normalize('NFC')` → UTF-8; abgeleiteter Schlüssel AES-GCM-256, nicht extrahierbar. Chiffre AES-GCM-256, 12-Byte-IV, 128-Bit-Tag.
- Umschlag (verschlüsseltes JSON): `{ format: "finanzklar-encrypted", version: 1, kdf: { name: "PBKDF2", hash: "SHA-256", iterations, salt }, cipher: { name: "AES-GCM", iv }, data }` (Base64). Der Kopf (`format, version, kdf, cipher`, feste Schlüsselreihenfolge, kanonisches JSON) ist AES-GCM-AAD: Manipulation an Parametern scheitert an der Authentifizierung. `decryptJSON` validiert streng (Namen exakt, Iterationen ganzzahlig in [600 000, 10 000 000], Salt 16 / IV 12 Byte) → „Unbekanntes Dateiformat.“ / „Die Datei ist beschädigt.“; Authentifizierungsfehler → „Passwort falsch oder Datei beschädigt.“.
- Vorbereitet für Teil B (nicht in der UI verdrahtet): `generateDataKey` (extrahierbar nur zum Wrappen), `wrapDataKey`/`unwrapDataKey` (AES-GCM, `wrapKey('raw')`; entpackter Schlüssel nicht extrahierbar), Wiederherstellungsschlüssel `generateRecoveryKey()` = 128 Bit als 26 Zeichen Crockford-Base32 in Vierergruppen (`XXXX-XXXX-…-XX`, ohne I/L/O/U), `normalizeRecoveryKey` (Großbuchstaben, Leer-/Bindestriche weg, O→0, I/L→1).
- Regeln: für jede Verschlüsselung ein frischer Zufalls-IV (nie wiederverwenden); Passwörter und Klartext nie loggen und nie in Modul-Variablen halten (nur kurz im Komponenten-State bis zur Ableitung); `encryptJSON(…, iterations)` erlaubt weniger Iterationen nur für Tests, `decryptJSON` lehnt < 600 000 ab; Base64 in Blöcken (kein Stack-Überlauf).
- Backup-UI: Einstellungen → Datensicherung → „Exportieren“ öffnet das Sheet „Backup exportieren“ (Passwort + Wiederholung, mind. 10 Zeichen, `autocomplete="new-password"`, Anzeigen-Knopf, Fortschritt „Wird verschlüsselt …“, Datei `finanz-backup-YYYY-MM-DD-verschluesselt.json`); „Ohne Passwort exportieren“ → ConfirmDialog mit Warnung → bisheriger Klartext-Export. Import: erkennt der Umschlag die Datei, fragt „Backup entschlüsseln“ (`current-password`) das Passwort, bei falschem Passwort Fehler im Sheet und neuer Versuch; danach unverändert `parseBackup` + „Alle Daten ersetzen?“. Klartext-Backups importieren wie zuvor.
- E2E: 118 Prüfungen (6 neu für verschlüsselte Backups).

## Projektgraph (Graphify)
- `graphify-out/GRAPH_REPORT.md` (Überblick: Kern-Abstraktionen, Module, Zusammenhänge) und `graphify-out/graph.json` (vollständiger Code-Graph) liegen im Repo. Neue Chats: zuerst den Report lesen statt alle Dateien zu öffnen; gezielt abfragen mit `graphify query "<Frage>"`, `graphify explain "<Symbol>"`, `graphify path "A" "B"`.
- Installation (falls nicht vorhanden): `uv tool install graphifyy` oder `pip install graphifyy` (Quelle: github.com/Graphify-Labs/graphify).
- Nach Code-Änderungen vor dem Commit aktualisieren – offline, ohne KI-Dienst: `GRAPHIFY_BACKEND=none graphify update .`
- Ist `graphify` nicht installiert (`command -v graphify` leer, z. B. in einer frischen Cloud-Sitzung), vor dem Aktualisieren neu installieren: `uv tool install graphifyy`, sonst `pip install graphifyy` (bei Bedarf in einem venv). Erst danach `update` ausführen.
- Lässt sich der Graph nicht aktualisieren (Installation oder `update` schlägt fehl), gilt `GRAPH_REPORT.md` als möglicherweise veraltet: Aussagen daraus (Symbole, Dateien, Zusammenhänge) vor dem Verwenden gegen den echten Code prüfen (Datei öffnen bzw. per Suche bestätigen) und dem Nutzer melden, dass der Graph nicht aktualisiert wurde. Stand prüfen: „Built from commit“ im Report mit `git rev-parse HEAD` vergleichen.
